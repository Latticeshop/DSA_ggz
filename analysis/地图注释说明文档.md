# DSA 地图说明文档

红警 3 日冕自走棋（`DSA_ggz`）的机制说明。

**为什么要有这个文件**：`lua/**` 里的注释会**原样进入** `ScriptsData.json` 的脚本 payload ——
合并器 `analysis/merge_passenger_spawn_payload.py` 只做文本拼接，不剥注释，而 WorldBuilder 每个
脚本节点只有一个 Lua 字符串、约 64KB 就会被截断（表现为 `<eof>` 报错）。之前 `PassengerLoadSpawn.lua`
24.6KB 里有 14KB 是注释，等于把一半预算花在注释上。

**注释分两类，去向不同**（用户 2026-10-03 定的口径）：

- **文本讲解**——讲机制、记实测依据、记失败过的路、写注意事项 → **不留在 lua，搬进本文档**。
  搬移工具 `analysis/tools/extract_lua_prose_comments.py`（默认 dry-run 列清单，`--apply` 才动手；
  逐行分型：中文句子=讲解，`{Type = ...}` / `@field` / lua 关键字开头=代码或注释掉的代码，留下）。
  被搬走的源文件顶部只留一行 `-- 讲解见 analysis/地图注释说明文档.md 附录 A.n`。
- **代码注释**——字段清单、参数说明、行尾提示、以及**注释掉的旧代码/停用数据表** → 留在 lua，
  跟代码一起进 payload（它们本来就该在代码旁边，也不算"讲解"）。

附录 A 按文件分节，每段标了**原行号 + 判定理由 + 后接代码**；正文 §1 按「函数名」定位，不按行号（行号会漂）。

新增/修改任何一条装车链路之前，先读 §1.13 的自检清单。

## 1. 载具装填（把步兵塞进卡池载具）

卡池本轮抽出的车要落地之后才 `ObjectFindObjects` 得到）。

### 1.2 载员来源：阵营已有的步兵，不新生成

- [需求] 用户 2026-10-03：「将随机步兵改为玩家拥有的步兵单位」。原来的做法是每轮自己
  `UNIT_SPAWN_NAMED_LOCATION_ORIENTATION` 造随机步兵，代价有两条：要占出兵配额，
  而且新兵会被抽卡流程改队带走（`PureDraw/04_draw.lua:567 PureDrawOnAIUnitBorn`：AI 阵营任意
  已注册模板出生 2 帧后，若在空投点 220 内就 `UNIT_SET_TEAM` 到 `<阵营>/ATTACK` 并升级）。
- [实测] **已经出生的步兵不会被本图任何流程吸入载具**，所以复用它们是安全的。
  那条空投改队的坑只挂在出生回调上，我们不新建单位就整体绕过了它——
  当年为此写的 `GetNextObjectId()` 预登记 / 事后认领代码已全部删除。
- 附带好处：不再需要航点/坐标（早先要按车的位置生成步兵），也不再和抽卡流程抢生成配额。

### 1.3 装车命令为什么必须「双引用名」

`lua/GAME/PassengerLoadSpawn.lua: g_PLSpawnGarrison`

```lua
ExecuteAction("SET_UNIT_REFERENCE", "Infantry1", unit)
ExecuteAction("SET_UNIT_REFERENCE", "Vehicle1", car)
ExecuteAction("NAMED_GARRISON_SPECIFIC_BUILDING_INSTANTLY", "Infantry1", "Vehicle1")
```

- 出兵流程造的兵是 `CREATE_OBJECT`：**不具名，只归队**，拿不到脚本名；卡池载具同样是地编/抽卡
  生成的，也没有脚本名。所以两个操作数都得先 `SET_UNIT_REFERENCE` 现设引用名。
- 引用名**同帧即可用**，也能当 NAMED_ 动作的主语。先例：本图正在跑的同款写法
  `devilASuper_0.lua:109-111` / `angelASuper_0.lua:109-111`（设引用名后紧跟具名装车）、
  `CenterTopBtnFunc.lua:848`，以及下面 §1.5 的 `DISABLE_UI_UNIT_ABILITY_BUTTON("Vehicle1", ...)`。
- 三个动作名就是本模块允许的全部动作（契约里限制「动作名总数不超过白名单三个」，防「顺手加一个」）。
  `NAMED_GARRISON` 只下发一次、只有这一个发出点，新逻辑必须复用它。

### 1.4 同帧判装车成败不可信 → 乐观下发 + 延迟巡收

- [实测 2026-10-03] 当时 IFV 日志报「装车未生效」，**但车的武器集确实变了**。本图没有任何流程会
  往卡池载具里塞兵（AI 不会自己上车），换武器集只能是那条 `NAMED_GARRISON` 生效了。
  也就是说命令是成功的，失败的是判据。
- 当时的两条同帧判据都读不回来：容器句柄比对 `ObjectGetContainerObject`、
  乘客数增长 `ObjectGetContainedPassengers`。判成失败之后又去 `NAMED_DELETE`，
  把**已经上车的兵**从车里删掉/弹出来 —— 这就是「步兵反复上下车拉扯」的真正根源。
- 正确做法：命令下发即占槽（`loaded + 1` 并登记台账），**不当场校验**；
  `delay_call(g_PLSpawnHold, g_PLSpawnHoldDelay=30)` 之后再复核。
- 复核只认引擎状态位：`EvaluateCondition("UNIT_HAS_OBJECT_STATUS", unit, "INSIDE_GARRISON")`。
  先例：参考地图筛「已经下车的兵」用的就是它（狭路相逢
  `Troop Deployment Initialization.lua:280 StatusBitFlagsExclude = "INSIDE_GARRISON"`）。
- [坑] Lua 里**数字 0 是真值**，`EvaluateCondition` 的返回值必须显式比成功值
  （`if inside == 1 or inside == true then`），不能直接 `if inside`。
- [坑] 位置查询在本引擎不可信（实测恒返回 0），所以既不用它找兵，也不用它判装车。

### 1.5 防下车 = 禁用下车按钮

`lua/GAME/PassengerLoadSpawn.lua: g_PLSpawnDisableEvac`、`g_PLSpawnEvacButtons`

- 参考地图「双兵种作战-狭路相逢」的「禁止下车」确实就是禁按钮，而且和本图用同一个动作名、
  同一种目标写法（目标都是刚 `SET_UNIT_REFERENCE` 出来的车）：
  `Troop Deployment Initialization.lua:133/181 ExecuteAction("DISABLE_UI_UNIT_ABILITY_BUTTON", 车名, "Command_Evacuate", 1)`，
  紧跟着装车语句之后下发。
- **下车指令在日冕里按兵种分别起名**，全图共 7 个（来源 `日冕地图lua例子/日冕单位信息汇总.txt` 的
  「技能代码」行）：`Command_Evacuate`、`Command_SovietBattleBunkerEvacuate`、
  `Command_SovietAntiGroundAircraftEvacuate`、`Command_CelestialGroundEvacuate`、
  `Command_AlliedAntiInfantryVehicleEvacuate`、`Command_DisguisedEvacuate`、
  `Command_SpecialPowerEvacuateShipPassengers`。
- [需求] 用户定：「不需要寻找对应关系，全禁即可」。**不做车种↔按钮名查表**，对处理到的每辆
  AI 车把这 7 个名字全下一遍；名字对不上这型车就是空操作，不报错。
  `SET_UNIT_REFERENCE` 设一次引用名后连发多条命令没问题。
- [需求] 「玩家的不用改」：禁用只在 side7/side8 的装填流程里下发，人类玩家的按钮一个都不碰。
- [实测] 禁完按钮，IFV / 联盟 / 重型都不再自己下车。**只有特洛伊要塞还会吐人**
  （第 4 轮 在外=5，样例 `活=1 在=0 车=0`），关按钮拦不住它。
  [已破案 2026-10-04] 当时读到「吐出来的人」其实多半是它**自带的标枪兵开火下车**，不是我们装进去的载员
  （见 §1.14），所以「关按钮对要塞无效」这个结论本身并不成立——只是那一轮没法区分两种兵。
  现在要塞在装车前先被清成空车，这一型不必再靠 `NoGetOff` 式的塞回兜底。

### 1.6 载员名单（白名单）与被剔除的兵种

`lua/GAME/PassengerLoadSpawn.lua: g_PLSpawnAllInf`，现在 14 个纯步兵模板。

- 这份名单同时就是**过滤器**：`g_PLSpawnCandidates` 用 `CreateObjectFilter{ SAME_PLAYER,
  IncludeThing = carEntry.Inf }` 一次把名单里的模板查全（多模板 `IncludeThing` 的先例
  `UNITCOUNTERINI_0.lua:336-348`）。**白名单不写名字就等于过滤**，所以源码里没有运行时黑名单
  那一遍判断——那是死代码。
- 模板名必须落在本图步兵区间 `UNITCOUNTERINI_0.lua` 的 `UNITLIST[1..step1]`（step1 = 20）里，
  并且要在玩家卡池（`PureDraw/02_data.lua`）里，否则过滤器写了本图不存在的名字等于白写。
  教训一：早先照抄双兵种地图的模板名（`AlliedEngineer` / `AlliedPeacekeeper` /
  `SovietFlakTrooper` / `AlliedJavelinSoldier` 等）在日冕里根本不存在，生成必然失败。
  教训二：`SovietMortarCycle`（火炮机车）是**载具**，排在步兵区间之后，别误当步兵收进来。
- 挑人要挡两路（`g_PLSpawnLoadCar` 里两条跳过）：
  1. 带 `INSIDE_GARRISON` 的跳过 —— 出兵流程每轮会把步兵装进**它自己的运兵车**，不跳等于抢人；
  2. 台账里已有 `UnitId` 的跳过 —— 装车命令同帧读不回状态，不查就会把同一个兵塞进两辆车。
- **随机起点**：`g_PLSpawnRandomIndex` 从名单里随机挑起点、扫完绕回开头。顺序扫会把名单靠前
  的兵种全塞满，满足不了「一个车 5 个槽位可以有不同的兵种进去」。
  Lua 4 没有 `table` 库也没有 `%` 运算符，取模自己算：`pick - floor((pick - 1) / count) * count`。
- **剔除名单（2026-10-03 实测后定，别再往回加）**：
  | 剔除项 | 日冕 ID | 原因 |
  |---|---|---|
  | 娜塔莎 / 百合子 / 谭雅 | `SovietCommandoTech1` / `JapanCommandoTech1` / `AlliedCommandoTech1` | 进车效果不好。`MICROINI_0.lua:370 CommandoNoStructureMICROCONTROL`（playindex 7/8，只筛 `FilterNoStructureCommando` = 百合子）每帧下换队/索敌/自动开火命令；`UnitCreate.lua` 又给三个 Commando 挂射程与索敌出生钩子。**被下令攻击或换队的乘车单位会下车**，表现为反复上下车 |
  | 警犬 / 战熊 | `AlliedScoutInfantry` / `SovietScoutInfantry` | 作战方式是激活型特殊技能（`Command_ActivateBarkSpecialPower` / `Command_ActivateRoarSpecialPower`），在车里没法正常表现 |
  | 爆裂机器人 | `JapanScoutInfantry` | 自爆投放类（`Command_JapanScoutInfantryBomb`） |
  | 天眼哨机 | `CelestialScoutDrone` | 挂睡眠针的哨机（`Command_ActivateSleepPin`），同类 |
  | 游骑兵 | `AlliedRangerInfantry` | 用户已把它整体移出生产/卡池（改走非生产表 T1），留在名单里等于写了个白名字，契约里「名单里的模板名都在玩家卡池里」那条会直接 FAIL |
- 这些兵照样受 `UnitCreate.lua:1264` 的战场寿命规则约束（AI 战斗单位默认 4 回合后 `NAMED_KILL`）。
  这是本图对 AI 单位的统一底层规则，**不做绕过**；乘员死了由巡收尾清位、下一轮按空位补。

### 1.7 载具配置与显示名对照

`lua/GAME/PassengerLoadSpawn.lua: g_PLSpawnCars`（`Template` / `Capacity` / `Inf` / `Tag`，可选 `BuiltIn`）

| Template | 日冕显示名 | Tag | Capacity |
|---|---|---|---|
| `AlliedAntiAirVehicleTech1` | 多功能步兵战车（IFV） | IFV | 1 |
| `AlliedBattleFortress` | 特洛伊突击要塞 | 要塞 | 5（先把自带的 4 个标枪兵清掉，见 §1.14） |
| `SovietAntiVehicleVehicleTech4` | 联盟重型坦克 | 联盟 | 5 |
| `Overlordtank` | 联盟重型坦克 | 重型 | 5 |

- **支持装车的是四型：IFV + 要塞 + 两型联盟**（`Overlordtank` 那辆地编守护者 `overlord7`/`overlord8`
  除外，见 §1.16）。
- `SovietAntiVehicleVehicleTech4` 与 `Overlordtank` **显示名重名**（都叫「联盟重型坦克」），
  所以日志用 `Tag` 区分这两型。相关：单位表由用户自维护，见 `analysis/` 与阶级表说明。
- **`BuiltIn` 只给「登场就自带载员」的车填**（现在只有要塞 = `AlliedAntiVehicleInfantry`）：
  填了它，本流程在装车之前会先把这些自带兵清成空车（`g_PLSpawnClearBuiltInCrew`，机制与判据见 §1.14），
  之后 `Capacity` 就按真实空位数写。IFV / 联盟 / 重型没有自带兵，**不要给它们加这个字段**。
- `Overlordtank` **不在玩家卡池**（`PureDraw/02_data.lua` 里没有它），本图以地图脚本对象
  `overlord7`/`overlord8` 的形式存在（`PurchaseTechMode_Logic.lua:42-45`）。找车是按阵营+模板名
  捞场上活着的车，不要求它来自卡池，所以这一行留着。**但 `overlord7`/`overlord8` 这两个地编对象
  已从装载目标里按脚本名剔除**（它们是 T3 塔守护者，见 §1.16）。
- [待实测] 如果某一模式下场上的 `Overlordtank` **只有** `overlord7`/`overlord8` 这两辆，剔除后
  「重型」这一行就没有目标，实际生效的会退化成「IFV + 联盟」两型；这属于预期行为，不是漏装。
- **牛蛙战车 `SovietAntiAirShip` / `SovietAntiAirShip_Ground` 没有配在这张表里**，也就是完全不碰
  （已实测跑通的是 IFV + 两型联盟；要塞 2026-10-04 带着「先清自带兵」重新进表，**待实测**）。
  要加就加一行，`Inf` 先直接指向 `g_PLSpawnAllInf`。
- 只复用卡池本轮已有的车，**绝不自己造车**：战斗单位跨回合不消失，造车会一直堆满场地
  （旧日志里的 PLV2/PLV6）。卡池载具确实有乘客位（诊断见过 车上=4）。
- IFV 的 `Capacity = 1` 是它的唯一载员位。**IFV 也用全量名单**：它的武器由载员的
  `IFVMode` 决定，没搭载步兵或该兵没有对应模式时，引擎回落到**默认武器**（用户提供的机制）。
  所以不需要为它收窄名单；原先收窄出来的那 12 个兵种反而正是「载员扣了、武器没改装」的嫌疑来源，
  `g_PLSpawnIFVInf` 已整表删除。
- 同理，「IFV 是吸收式乘员（载员不占乘客位）」这个猜测也已被实测否掉：连装 16 人（含 IFV 的 1 格）
  巡收回来全是 在车=16、消失=0，IFV 载员照样是带 `INSIDE_GARRISON` 的正常对象，
  所以台账不再单记「被吸收」的占用位。

### 1.8 台账数据结构

`lua/GAME/PassengerLoadSpawn.lua: g_PLSpawnEntries`，条目 `{ CarId, UnitId, Tag, Retry }`

- **只能用数组，不能用 `[carId] = {...}` 字典**：Lua 4 没有 `pairs`，收尾只能按下标遍历、
  整表重建来清条目。某辆车占了几位靠扫 `CarId` 统计（`g_PLSpawnTrackedCount`）。
- 一份数据三用：① 这辆车已被我们占了几个位；② 待巡收回执的队列；③ 本轮挡住
  「这个兵已经被前面那辆车占走」（`g_PLSpawnTrackedUnit`）。
- 空位数 `g_PLSpawnFreeSlots` = `Capacity - max(引擎读回的乘客数, 台账条数)`，取较大者是两路证据
  都信（车自己可能载人，我们的命令同帧又读不回来）。**宁少装，不重复装**。

### 1.9 巡收的四种去向（兵一律不删）

`lua/GAME/PassengerLoadSpawn.lua: g_PLSpawnHold`

| 判定 | 处理 |
|---|---|
| 在车（`INSIDE_GARRISON`） | 留在台账继续占位，`Retry` 清零（保证「连续塞 N 次」是连续计数） |
| 对象不在了 | 当阵亡处理，槽位腾出来，下轮按空位补 |
| 活着但在车外 | 被弹出来了。按参考地图 `NoGetOff()`（`Troop Deployment Initialization.lua:300`，间隔 `t*15` 帧把车附近不带 `INSIDE_GARRISON` 的己方步兵再塞回去）的做法**重下装车命令塞回** |
| 塞 `g_PLSpawnHoldTries`(2) 次仍在外面 / 车没了 | 清条目**放手**，兵回战场打仗，下一轮重新挑 |

- [需求] 载员是本方战斗单位，**装填与巡收这两条路一个删除动作都没有**（兵装不上就回战场打仗，
  和参考地图 `NoGetOff` 的区别就在这里：那边塞不进就删，这边直接不管）。
  全链路唯一的删除点是 `g_PLSpawnClearBuiltInCrew`（清要塞自带的标枪兵，见 §1.14），
  契约把它钉死成「`NAMED_DELETE` 只在这一个函数里出现」。

### 1.10 会「装上又被弹出来」的四个来源（都是本图自己的流程）

1. **碰出兵流程的队**：`<阵营>/INFANTn` 每轮被 `SPUNITINI_0.lua:24-47`（`LandArmySpawn.lua:114`

### 1.14 自带载员：特洛伊要塞先把 4 个标枪兵清成空车

[需求] 用户 2026-10-03：特洛伊要塞不管是生产、直接生成还是回合开始刷兵，登场时内部就带着
4 个标枪兵（`AlliedAntiVehicleInfantry`；注意 `AlliedAntiInfantryInfantry` 是维和步兵，

**拉扯真因（2026-10-04 破案）**：要塞**开火**时自带标枪兵会走出车体打一枪再回车，不开火就完全不出来。
走出来的那段时间它们**不带 `INSIDE_GARRISON`**，于是被我们的流程当成普通空步兵接手：

1. `g_PLSpawnCandidates` 把它们挑中 → `g_PLSpawnGarrison` 塞进 IFV / 联盟；
2. 下一轮巡收 `g_PLSpawnHold`（§1.9）读到「活着但在车外」→ 按参考地图 `NoGetOff` 的手法**再塞回去**；
3. 引擎/要塞又把人拉回自己车里。

⇒ 用户看到的「要塞内部的步兵下车又上车、反复拉扯」，位置就在要塞周围。
判据是这条拉扯**跟「有没有给要塞装车」无关**：2026-10-04 上午把要塞整行清出装载列表之后依然拉扯，
所以不是装车下发动作的 bug，而是**自带兵被卷进了装填流程**（`AlliedAntiVehicleInfantry` 本来就在
§1.6 那份全量白名单里）。

**现在的做法**（用户方案：「清空自带的步兵，然后像联盟等空载具一样使用我们成熟的装兵机制，
还能实现 5 个位置随机装兵」）：

1. `lua/GAME/PassengerLoadSpawn.lua: g_PLSpawnClearBuiltInCrew(sideIndex, cars, count, carEntry)`，
   在 `g_PLSpawnFillType` 里**找到本轮这型车之后、逐车装填之前**调用：
   按 `carEntry.BuiltIn` 查本阵营的标枪兵（`CrewFilter` 建一次缓存在条目上），
   只有 `ObjectGetContainerObject(兵)` 返回容器的**对象 ID 命中本轮这批要塞**时，
   才 `NAMED_EXIT_BUILDING` + `NAMED_DELETE`（用户选**静默移除**，不用 `NAMED_KILL`：后者会留尸体与击杀播报）。
   - **判据故意写成反向**（从兵看容器），因为正向的 `ObjectGetContainedPassengers(要塞)` 读不回这些
     自带兵（下面「弯路」第一条的实测）。`ObjectGetContainerObject` 用于标枪兵这类乘员是有先例的：
     日冕参考 `日冕 Lua.lua:319-324`，本图 `UNITCOUNTERINI_0.lua` 的回收扫描也信它。
   - 反向判据同时挡住两类误删：玩家自己造的标枪兵（容器为 nil）、已被我们装进 IFV/联盟的标枪兵
     （容器是别的车，ID 不在这批要塞里）。
   - 时机在**回合开头延迟 30 帧、刚刷出来还没开火**的窗口（§1.1 的时序前提），
     不在兵正走出车体开火的瞬间删人。
   - **这是整条链路唯一的删除动作**（§1.9）：删的是要塞自带的兵，不是我们挑去装车的载员。
     契约按「`NAMED_DELETE` 只在这一个函数里出现 + 装填与巡收两条路零删除」钉住，
     并要求 `NAMED_EXIT_BUILDING` 在前、清兵调用在装填循环之前。
2. `g_PLSpawnCars` 里要塞恢复 **`Capacity = 5`** 并带 `BuiltIn = "AlliedAntiVehicleInfantry"`：
   自带兵清完它就是空车，走和联盟一模一样的装填 / 巡收 / 禁按钮流程，5 个位子随机装兵。
3. **回收侧那 4 个标枪兵的额度扣减已撤掉**（用户 2026-10-04 定）。原来那套
   `g_BuiltInCrew` 登记表 + `crewOwed` 累计 + 计数循环后 `RemoveRecycleUnitCount(playindex, {Type=...}, owed)`
   已从 `lua/LUABOX/UNITCOUNTERINI_0.lua` **整段删除**（契约反向断言它不许回来），
   原因：载员要在**入池之前**就被装车流程清掉，池子里根本不会多出 4 份标枪兵额度，扣减失去前提。
   `RemoveRecycleUnitCount` 本体在 `lua/GAME/RecycleUnit.lua:457`，符文与按钮那条路还在用，没动。
   [待实测] 清除点在延迟 30 帧的装填里，而回收扫描（`UNITCOUNTERINI_0.lua: unitgenerate` →
   `unitgetcountanddelet`，先 `NAMED_EXIT_BUILDING` 再计数 + `NAMED_DELETE`）在更早的回合流程里跑；
   实测若仍看到「回收要塞白赚 4 份标枪兵额度」，说明这批兵还是先被扫描入池了，届时再回到
   「扫描计数末尾扣额度」那一版（就是上面被删掉的 `g_BuiltInCrew`）。

**走过的两条弯路（别再试）**：

- **调 `Capacity`**：[实测] 要塞 5 个位子登场即被 4 个自带兵占着，按 5 塞会把自带兵挤出又下不了车、

  因为读不到占用这件事本身就没解决。现在清空了自带兵，`Capacity = 5` 才是真实空位数。
- **整行清出装载列表**（2026-10-04 上午）：不装要塞之后拉扯**依然存在**，反而把真因指到自带兵身上（见上）。
  这一版当时还留着回收侧的额度扣减，现在一并撤了。

### 1.15 两个 AI 阵营的装车必须互不干扰（跨阵营拦人）

[实测] 用户 2026-10-03（登神测试局）：本方（side7）每回合场上只有 1 个磁暴部队，对面（side8）
有联盟坦克（5 个载员位），结果**本方步兵整批从场上消失**（用户描述为「扣除了」或「被转移了」）。
两个中间 AI 的装车本该各管各的，所以这是 bug。

- 症状推断：`g_PLSpawnFindCars` / `g_PLSpawnCandidates` 都只靠
  `ObjectFindObjects(P[sideIndex], nil, 过滤器)` + `Relationship = "SAME_PLAYER"` 圈阵营。
  这一条一旦在本引擎里没把两个阵营分干净（两边的对象同时进同一张列表），side7 那一趟就会把
  列表里排在前面的**对面的车**当成自己的车、再把自己列表里的兵塞进去，side8 那一趟同理。
  联盟坦克 5 个位子一次能吃掉 5 个步兵，几轮下来本方步兵就全没了。
- 改法：两张列表查出来之后都过一遍 `g_PLSpawnKeepOwnSide(objects, count, sideIndex)`，
  用 `ObjectPlayerScriptName(obj)` 按阵营收窄；`g_PLSpawnSideNames` 登记
  `[7] = "PlyrCivilian"`、`[8] = "PlyrCreeps"`。
- 判据故意写成**只挡对面、不做正向匹配**（怕「必须等于本阵营名」把返回异常名字的对象全丢掉、
  整条链路掐死）。`ObjectPlayerScriptName`
  的用法先例：`PureDraw/04_draw.lua:506-519`（靠它判 `PlyrCivilian` / `PlyrCreeps`，再决定
  `<阵营>/ATTACK` 队），返回值对两个 AI 阵营就是上面这两个脚本名。
- **车侧、兵侧两条路都要过滤**：只过滤一侧仍会留下「本方兵塞进对面车」或「对面兵塞进本方车」。
- **巡收这一层也要挡一次**：`g_PLSpawnEntries` 只存数字 `CarId`/`UnitId`，而**引擎会复用对象 ID**
  （同样的坑在 `海克斯符文系统设计.md` 里已经写明：诸神黄昏的登记要「清掉阵亡或被复用 objectId
  的登记」）。`g_PLSpawnHold` 用 `GetObjectById` 现取句柄，于是可能配成「对面那辆车 + 本方的兵」，
  再按这个配对补一次装车——这条路绕过了上面那张按阵营过滤的名单，所以单独加 `g_PLSpawnCrossPair(car, unit)`
  挡一次：车名与兵名都在 `g_PLSpawnSideNames` 里、且互不相同时才算「明确跨阵营」，命中就把车当没了
  （整条放手，兵不删）。判据只认「两个 AI 阵营名对不上」，任一侧返回别的名字都不算跨阵营，
  所以不会误伤正常配对。
- 巡收这一层除了上面这条跨阵营配对，不再加别的判据，就不会动到「兵不删、下车重塞」这条既有语义。
- **按阵营过滤挡不住「本来就同阵营的车」**：地编预制的守护者坦克正是这一类，见 §1.16。

### 1.16 吞兵真因：地编预制的 overlord7 / overlord8 是合法的装载目标

[实测] 用户 2026-10-03 深夜破案：**装车逻辑本身没有问题**，问题在地图上有两辆地编预制的旧版联盟坦克
`overlord7` / `overlord8`（`lua/GAME/BasicVar1.lua:35-40` 的 `towerGuardianNames`，T3 塔被摧毁时的
守护者，另有 `cams/DeathMode.lua:64-66`、`GAME/PurchaseTechMode_Logic.lua:42-44` 按脚本名取它们）。
它们满足装车的全部条件：模板就是表里的 `Overlordtank`，归属就是 `PlyrCivilian` / `PlyrCreeps`
两个 AI 阵营之一，而且**自带 5 个空载员位**。回合初期一轮 pass 就把它们当成"本方的空车"填满，
玩家看到的表现是"我的兵刚刷出来就少了"。

- 为什么按阵营过滤挡不住（§1.15）：它们不是跨阵营对象，`g_PLSpawnKeepOwnSide` 与
